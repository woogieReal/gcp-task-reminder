# 프로젝트 초기 세팅 작업계획

## 목표

이후 task(예약 API, 인증, 웹 UI)가 올라갈 Node.js/TypeScript 프로젝트 골격을 만든다.
환경 변수 검증(`config.ts`)과 `/healthz`만 가진 최소 Express 앱, 타입 검사·테스트 도구, Docker 기반 로컬 개발 환경과 배포용 이미지 정의까지 갖춰
`/check-task`가 이후 모든 task에서 `typecheck`·`test`로 자동 검증할 수 있는 기반을 마련한다.

## 작업 범위

- 블루프린트 task 2: 프로젝트 골격(`package.json`, `tsconfig.json`), 테스트 도구(vitest, supertest), `config.ts`, `/healthz`
- 블루프린트 Phase 4: `Dockerfile`(deps/dev/build/runtime), `.dockerignore`, `compose.yaml`
- 블루프린트 Phase 5: `.env.example`, 로컬 실행 절차 확인
- 블루프린트 6장 테스트 원칙: 앱 생성 함수와 서버 기동(`listen`) 분리
- 제외: 예약 API·텔레그램(task 3), 인증·보안 헤더(task 4), `public/` 웹 페이지(task 5), CI 워크플로(task 6)

## 세부 작업 목록

### 1단계: 프로젝트 골격

- [x] `package.json` 작성: `"type": "module"` 여부 결정, Node 22 엔진 명시, scripts `build`·`start`·`dev`·`typecheck`·`test`
  - 결과: ESM(`"type": "module"`) 채택. Node 22 + TypeScript `NodeNext`의 기본 방식이며 import 경로에 `.js`를 붙인다
- [x] 의존성 설치: 런타임 `express`, 개발 `typescript`·`tsx`·`vitest`·`supertest`·`@types/express`·`@types/node`·`@types/supertest` (`package-lock.json` 생성)
  - 결과: express 5.3, typescript 7.0, tsx 4.23, vitest 5.0, supertest 7.3, @types/node 22
- [x] `tsconfig.json` 작성: strict, Node 22 대상, `src/` → `dist/` 빌드, 테스트 파일은 빌드 결과에서 제외
  - 결과: 타입 검사용 `tsconfig.json`(테스트 포함)과 빌드용 `tsconfig.build.json`(테스트 제외)으로 분리
  - 이슈: `.gitignore`의 `*.json` 규칙(서비스 계정 키 차단용)이 `tsconfig.build.json`을 막아 CI 빌드가 실패할 수 있어 예외 규칙 추가
- [x] 블루프린트 디렉터리 구조에 맞춰 `src/` 생성 (이번 task에서는 `index.ts`, `app.ts`, `config.ts`만)

### 2단계: 환경 변수 검증 (`config.ts`)

- [x] 필수 10개(`GCP_PROJECT_ID`, `GCP_LOCATION`, `GCP_QUEUE_NAME`, `SERVICE_URL`, `TASKS_INVOKER_SA_EMAIL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `GOOGLE_OAUTH_CLIENT_ID`, `ALLOWED_EMAIL`, `SESSION_SECRET`) 로드, 하나라도 없거나 빈 값이면 누락된 변수 이름을 모두 알려주는 에러
- [x] 선택 값: `PORT`(기본 8080, 숫자 검증), `NODE_ENV`(기본 `production`), `SKIP_TRIGGER_AUTH`(`NODE_ENV=development`이고 값이 `true`일 때만 활성)
- [x] 에러 메시지·로그에 환경 변수 값이 출력되지 않도록 이름만 표시
- [x] `process.env`를 직접 읽지 않고 입력 객체를 받는 함수로 만들어 테스트에서 주입 가능하게 함

### 3단계: 최소 Express 앱

- [x] `app.ts`: 설정을 받아 Express 앱을 만드는 함수, `GET /healthz` → `200`, 알 수 없는 경로 → `404` `{ "error": "Not Found" }`, 처리되지 않은 에러 → `500` `{ "error": "Internal Server Error" }`(스택·내부 메시지 미노출)
- [x] `index.ts`: 설정 로드 실패 시 에러 출력 후 종료 코드 1로 종료, 성공 시 `PORT`로 `listen`, SIGTERM 수신 시 정상 종료 (Cloud Run 인스턴스 종료 대응)

### 4단계: 테스트

- [x] `config` 테스트: 필수 값 모두 있음 → 성공, 하나 누락·빈 값 → 실패하고 누락 이름 포함, 에러 메시지에 값 미포함, `PORT` 기본값·숫자 아님 → 실패, `SKIP_TRIGGER_AUTH`가 production에서 무시됨
- [x] `app` 테스트(supertest): `/healthz` `200`, 없는 경로 `404` JSON
- [x] `npm run typecheck`, `npm test` 통과

### 5단계: 컨테이너와 로컬 개발 환경

- [x] `Dockerfile`: `node:22-slim` 기반 `deps` → `dev` / `build` → `runtime`(기본 타깃, 운영 의존성만, `dist/` 복사, `NODE_ENV=production`, 비root 사용자). `public/`은 아직 없으므로 task 5에서 복사 단계를 추가
- [x] `.dockerignore`: `node_modules`, `dist`, `terraform`, `.env*`, `.git`, `docs`
- [x] `compose.yaml`: `api` 서비스, `dev` 타깃, 8080 포트, `.env` 주입, `src/` 마운트(핫 리로드), ADC 파일 읽기 전용 마운트 + `GOOGLE_APPLICATION_CREDENTIALS`, `node_modules`는 이미지 것 사용
- [x] `.env.example`: 블루프린트 Phase 5 표의 변수와 로컬 값 (비밀값은 자리표시자)
- [x] **확인:** `.gitignore`의 `.env*` 관련 규칙이 `.env.example`을 막지 않는지 (`git check-ignore`)
  - 결과: `.env.example`은 추적 대상, `.env`는 ignore 확인

### 6단계: 동작 확인

- [x] `docker build`로 `runtime` 이미지 빌드 성공, 컨테이너 실행 시 `/healthz` `200`, 실행 사용자가 root가 아님
- [x] `.env` 작성(README 절차) 후 `docker compose up --build` → `http://localhost:8080/healthz` `200`
- [x] 컨테이너 실행 중 `src/` 수정 시 자동 재시작(핫 리로드) 확인
- [x] 필수 환경 변수 하나를 빼고 실행 시 컨테이너가 누락 이름을 출력하고 종료하는지 확인
- [x] README 로컬 실행 절차와 실제 동작이 일치하는지 확인, 다르면 README 수정
  - 결과: README 4번 절차(복사 → 토큰·세션 키 채우기 → `docker compose up --build`)대로 동작 확인, 수정 불필요

## 완료 기준

- `npm run typecheck`, `npm test`, `npm run build`가 모두 통과한다
- 필수 환경 변수가 하나라도 없으면 앱이 누락된 변수 이름만 출력하고 종료 코드 1로 종료한다 (값은 출력하지 않음)
- `docker compose up --build` 후 `http://localhost:8080/healthz`가 `200`을 반환하고, `src/` 수정 시 자동 재시작된다
- `runtime` 이미지가 빌드되고, 실행 시 `/healthz` `200`, 비root 사용자로 동작한다
- `.env`는 Git에 추적되지 않고 `.env.example`은 추적된다
