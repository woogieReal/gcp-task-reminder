### 주요 결정 사항
- **ESM(`"type": "module"`) 채택:** Node 22와 TypeScript `NodeNext`의 기본 방식이다. import 경로에 `.js` 확장자를 붙여야 하는 대신 Node 런타임과 동작이 일치한다.
- **앱 생성(`app.ts`)과 서버 기동(`index.ts`) 분리:** supertest가 포트를 열지 않고 앱을 직접 호출할 수 있게 해 블루프린트 테스트 원칙을 따랐다. 이후 task에서 서비스 의존성을 이 함수에 주입한다.
- **`loadConfig`가 `process.env` 대신 입력 객체를 받음:** 테스트에서 환경 변수를 오염시키지 않고 경계값을 검증할 수 있다.
- **누락 변수는 이름만 출력:** 로그에 비밀값이 섞이지 않게 하면서, 누락된 변수를 한 번에 모두 보여줘 설정 수정을 빠르게 한다.
- **`SKIP_TRIGGER_AUTH`는 `NODE_ENV=development`에서만 활성:** runtime 이미지는 `NODE_ENV=production`으로 고정되므로 배포 환경에서 실수로 켜질 수 없다.
- **tsconfig 2개로 분리:** 타입 검사는 테스트까지 포함하고, 빌드 결과(`dist/`)에는 테스트 파일이 들어가지 않게 했다.
- **runtime 스테이지는 새 베이스에서 운영 의존성만 설치:** 이미지 크기를 줄이고 devDependencies가 배포 이미지에 들어가지 않게 했다. 비root(`node`) 사용자로 실행한다.
- **compose는 이미지의 `node_modules` 사용, `src/`만 마운트:** 호스트와 컨테이너의 네이티브 모듈 차이를 피한다. 의존성 변경 시에는 `--build`로 다시 빌드한다.

### 이슈 & 해결
- **`.gitignore`가 `tsconfig.build.json`을 차단:** 서비스 계정 키 유출을 막는 `*.json` 규칙 때문에 새 설정 파일이 Git에 올라가지 않아, CI(GitHub Actions)에서 빌드가 실패할 수 있었다. 예외 규칙 `!tsconfig.build.json`을 추가하고, 추적 대상 파일만으로 구성한 깨끗한 체크아웃에서 이미지가 빌드되는 것을 확인했다.
- **핫 리로드 검증 방법:** 실행 중 `src/app.ts`의 응답을 임시로 바꿔 반영되는 것을 확인한 뒤 원복했다.
- **다음 task로 이월:** 500 에러 핸들러 자동 테스트(라우트가 생기는 task 3), runtime 이미지의 `public/` 복사(task 5).
