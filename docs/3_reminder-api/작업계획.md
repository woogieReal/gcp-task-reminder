# 예약 API 구현 작업계획

## 목표

이 프로젝트의 핵심 학습 대상인 Cloud Tasks 지연 실행을 실제로 동작시킨다.
예약 생성·조회·취소 API(`/api/reminders`)와 Cloud Tasks가 호출하는 `/trigger`, 텔레그램 발송 모듈을 구현하고,
외부 연동은 주입 가능한 서비스로 분리해 자동 테스트에서는 mock으로, 로컬에서는 실제 큐와 텔레그램으로 검증한다.

## 작업 범위

- 블루프린트 Phase 2 중 `POST`·`GET /api/reminders`, `DELETE /api/reminders/:id`, `POST /trigger`
- `src/services/task.service.ts`(Cloud Tasks 생성·조회·삭제), `src/services/telegram.service.ts`(sendMessage)
- `src/routes/reminder.routes.ts`, `src/routes/trigger.routes.ts`, 입력 검증
- task 1에서 이월: `cloudtasks.tasks.fullView` 권한 확인 (없으면 `terraform/iam.tf` 보완)
- task 2에서 이월: 500 에러 핸들러 자동 테스트
- 제외: 세션 인증·`/trigger` OIDC 검증·CSRF·보안 헤더(task 4), 웹 페이지(task 5), 배포(task 6)
- **보안 전제:** 이 task의 `/api/*`와 `/trigger`는 인증이 없으므로 로컬에서만 실행한다. Cloud Run에는 task 4 완료 전까지 배포하지 않는다.

## 세부 작업 목록

### 1단계: 사전 확인

- [x] **확인:** 런타임 SA에 부여한 역할(`cloudtasks.enqueuer`, `cloudtasks.viewer`, `cloudtasks.taskDeleter`)에 `cloudtasks.tasks.fullView` 권한이 포함되는지 `gcloud iam roles describe`로 확인. 없으면 해당 권한을 가진 최소 역할을 `terraform/iam.tf`에 추가하고 사용자에게 apply 요청
  - 결과: `cloudtasks.viewer`와 `cloudtasks.enqueuer` 모두 `cloudtasks.tasks.fullView` 포함 → Terraform 변경 불필요
- [x] 의존성 설치: `@google-cloud/tasks`, `axios`

### 2단계: 서비스 모듈

- [x] `task.service.ts`: 인터페이스(`create`, `list`, `delete`)와 Cloud Tasks 구현
  - 생성: 대상 `${SERVICE_URL}/trigger`, POST, `Content-Type: application/json`, 본문 `{ text }` Base64, `scheduleTime`, OIDC(발급 SA = invoker SA, audience = `SERVICE_URL`). 태스크 이름은 자동 생성
  - 조회: FULL 뷰로 큐 전체 조회(페이지 자동 순회), 본문에서 `text` 복원, `id`(태스크 ID), `scheduleAt`, `attempts`(디스패치 횟수), `lastError`(마지막 시도 실패 상태) 반환, 예약 시각 오름차순
  - 삭제: 태스크 ID와 큐 경로를 조합해 삭제, Cloud Tasks `NOT_FOUND`는 "없음"으로 구분해 반환
- [x] `telegram.service.ts`: `sendMessage(text)` → `chat_id = TELEGRAM_CHAT_ID`, `text = "[리마인더] <text>"`, 서식 해석 없음(plain text), 타임아웃 설정. 실패 시 상태 코드와 메시지만 담은 에러 (토큰이 포함된 URL 미노출)

### 3단계: 라우트와 검증

- [x] `createApp`이 설정과 서비스(task, telegram)를 주입받도록 변경, `index.ts`에서 실제 구현 연결
- [x] JSON 본문 파서 (크기 제한), 잘못된 JSON은 `400`
- [x] `POST /api/reminders`: `text`(공백 아님, 최대 4000자), `scheduleAt`(UTC 오프셋 포함 ISO 8601, 현재 이후, 30일 이내) 검증 → `201` `{ id, text, scheduleAt }`
- [x] `GET /api/reminders` → `200` 배열
- [x] `DELETE /api/reminders/:id`: ID 형식(영문·숫자·`-`·`_`) 검증 → `204`, 없으면 `404`
- [x] `POST /trigger`: `X-CloudTasks-TaskName`·`X-CloudTasks-TaskRetryCount` 로그, 발송 성공 `200`, 본문 오류 `200` + 에러 로그, 텔레그램 실패 `500`
- [x] Cloud Tasks 호출 실패 등 예상하지 못한 에러는 공통 500 핸들러로 처리 (내부 메시지 미노출)

### 4단계: 자동 테스트 (외부 API는 mock)

- [x] 예약 생성: 정상 `201`, `text` 누락·공백·4000자 초과 → `400`, `scheduleAt` 누락·형식 오류·오프셋 없음·과거·30일 초과 → `400`
- [x] 생성 시 태스크 구성 확인: 대상 URL, 메서드, 헤더, 본문(Base64 디코딩 결과), 예약 시각, OIDC 발급 SA·audience
- [x] 예약 목록: 서비스 결과를 그대로 반환, 본문 복원·정렬 로직 단위 테스트
- [x] 예약 취소: 정상 `204`, ID 형식 위반 → `400`, 없는 태스크 → `404`
- [x] `/trigger`: 텔레그램 성공 `200`, 실패 `500`, 본문 오류 `200`(발송 안 함)
- [x] 텔레그램 서비스: 요청 URL·본문(접두어 포함), 실패 시 에러 메시지에 토큰 미포함
- [x] 500 핸들러: 서비스가 던진 에러의 내부 메시지가 응답에 노출되지 않음
- [x] `npm run typecheck`, `npm test`, `npm run build` 통과

### 5단계: 로컬 수동 검증 (실제 큐·텔레그램)

- [x] `docker compose up --build` 후 `POST /api/reminders`(1일 뒤 시각)로 실제 큐에 태스크 생성 → `gcloud tasks list`로 확인 (대상 URL, OIDC 설정 포함)
  - 1차: Docker Desktop이 꺼져 있어 호스트에서 같은 `.env`로 `tsx` 실행해 검증
  - 2차: Docker Desktop 재기동 후 compose 컨테이너에서 동일 시나리오 재검증 (마운트된 ADC로 Cloud Tasks 인증 동작 확인, 태스크 ID `57165477772552146501`)
  - 결과: `201` 태스크 ID `68120193892640931411`. `gcloud tasks describe`로 대상 `…run.app/trigger`, POST, OIDC(invoker SA, audience = Cloud Run URL), 예약 시각 일치 확인
- [x] `GET /api/reminders`에서 방금 만든 예약의 `text`가 복원되어 보이는지 확인
  - 결과: 한글 `text`, `scheduleAt`, `attempts: 0` 정상 반환
- [x] `DELETE /api/reminders/:id` → 큐에서 사라짐 확인, 같은 ID 재삭제 → `404`
- [x] `SKIP_TRIGGER_AUTH=true` 상태에서 로컬 `/trigger` 직접 호출 → 텔레그램 `[리마인더] ...` 수신 확인
  - 결과: 호스트·compose 두 번 모두 `200 {"status":"sent"}` (텔레그램 API 성공 응답). 서버·컨테이너 로그에 봇 토큰 미포함. 사용자가 두 메시지 모두 휴대폰에서 수신 확인
- [x] 검증 후 큐에 테스트 태스크가 남지 않았는지 확인
  - 결과: `gcloud tasks list` 0건

## 완료 기준

- `npm run typecheck`, `npm test`, `npm run build`가 모두 통과하고, 블루프린트 6장의 task 3 자동 테스트 케이스가 모두 포함된다
- 로컬 compose에서 실제 큐에 예약 생성 → 목록에 `text` 표시 → 취소 → 큐에서 사라짐이 확인된다
- 로컬 `/trigger` 호출로 텔레그램 알림을 실제로 수신한다
- 런타임 SA가 FULL 뷰 조회 권한을 갖는지 확인되어 있다 (필요 시 Terraform 반영 및 apply 완료)
- 응답과 로그에 봇 토큰이 노출되지 않는다
